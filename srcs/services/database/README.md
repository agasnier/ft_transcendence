# Database

`database` is a **MariaDB** server, the single store behind the whole project. It is not exposed to the external network: it lives on the internal Docker network and only the backend services reach it.

## Persistent data

The data must survive a container restart or rebuild, so it does not live inside the container. The `db_data` Docker volume bind-mounts the host directory `./data/mariadb` onto `/var/lib/mysql`, where MariaDB writes everything. Stopping or rebuilding the container leaves that directory untouched.

Wiping the database is therefore deleting that directory, not restarting the container. As `database` container runs in root, Makefile need `sudo` to delete this directory

The root password is passed as a **Docker secret** (`/run/secrets/db_root_password`) through `MARIADB_ROOT_PASSWORD_FILE`, and the name of the application database comes from `./env/.env`.


## Connection to database via vault

No service ever connects with the root account, and there is no fixed password shared between the database and the services. The credentials are **dynamic**, generated by Vault on demand.

For Vault to create those users, it needs an account of its own. The `tools/entrypoint.sh` script sets it up at first boot. It creates a `vault@'%'` user and grants it `CREATE USER ON *.*` plus `ALL PRIVILEGES` on the application database `WITH GRANT OPTION`.

From there, Vault's database engine logs in as user `vault` and creates a short-lived SQL user each time a service asks for credentials. 

## Creating tables via ORM

The database ships **empty**: this service defines no schema and no table. Each backend service owns and creates its own tables, through an ORM, when it runs its migrations against this database:

|Services		|Tables			      |
|---				|---				   	|
|users_service |users   	      	|
|              |jwt_refresh_token	|
|api_service	|api_keys         	|
